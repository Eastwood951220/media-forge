# 首页仪表盘首次加载优化

## 目标与现状

缩短首页概览首次请求的等待时间，保留现有统计口径和页面内容。当前 `/api/dashboard/overview` 串行构建爬虫、运行、影片和存储模块，前端在整个响应返回后才展示数据。本地库约有 85 个爬虫任务、195 条运行记录、32,323 条运行明细和 26,053 部影片。最新运行查询因 ORM 的 `selectin` 关系额外加载明细；本地测得该查询约 1.29 秒，显式禁用明细加载后约 0.009 秒。影片榜单读取全部影片所需字段并在 Python 中统计，约 0.44–0.66 秒。当前本地 HTTP 服务的健康请求也超时，尚不能用页面请求时间作端到端基线。

## 方案比较

- **只优化查询**：裁剪仪表盘不使用的 ORM 关联加载，保留榜单每次现算。冷请求直接受益，榜单仍随影片量线性增长。
- **查询优化加 Redis 短期缓存（选定）**：先裁剪查询，再仅缓存全局影片榜单 5 分钟。重复请求无需扫描全部影片；缓存未命中时仍按现有逻辑计算。
- **物化视图**：预聚合榜单后读取最快，但需迁移、刷新机制和失败恢复；当前规模下引入成本较高。普通视图仍会实时执行聚合，不能单独解决等待时间。

## 改动范围

1. 仪表盘使用的任务状态和近期运行查询不加载任务 URL、运行明细等未使用关系；共享运行状态接口的返回结构与统计口径保持不变。对相关查询使用局部加载选项，避免改动模型的全局关系定义。
2. 仅对影片榜单使用全局 Redis 缓存，键带版本号，TTL 300 秒。影片总数和存储状态、爬虫/运行/存储任务状态、告警及刷新时间继续实时读取。缓存缺失时从数据库重算并回填；Redis 读写异常时退回数据库计算，概览仍可返回。
3. 保留 `/api/dashboard/overview` 的已有字段和刷新按钮行为，仅新增榜单更新时间字段。手动刷新会重新请求接口，但榜单在 5 分钟窗口内可能沿用缓存；其余指标照常更新。
4. 根据用户后续要求，在内容排名区域显示榜单的实际计算时间。缓存命中时沿用缓存中的时间；缓存失效重算后更新时间。页头现有的概览刷新时间继续表示本次请求时间。

## 验证与边界

补充针对 ORM 关联加载、缓存命中/过期/Redis 不可用及榜单更新时间的后端测试，并验证前端时间展示。运行仪表盘及相关爬虫状态测试。对比冷缓存和热缓存的模块耗时，并在 HTTP 服务恢复响应后再做接口级测量。缓存可能暂存 5 分钟内的旧榜单，这是已接受的延迟；若需要强制即时刷新榜单，需另行定义失效触发点。
