# 爬虫实时状态与接口数据边界优化设计

## 背景

当前爬虫任务列表、运行记录列表和运行详情同时从 REST 接口与
EventSource 获取部分相同数据，造成以下问题：

- 任务列表同时请求列表和计数接口，列表响应还内嵌运行态；组件本地状态、
  Zustand Store 和 EventSource 又分别保存或更新同一份状态。
- 运行记录列表同时请求列表和计数接口，并把实时事件直接写入 Query 缓存，
  与已经存在的运行态 Store 职责重叠。
- 运行详情分别请求运行信息、日志、子任务列表和子任务汇总；
  `crawler.run.detail.updated` 又重复发送完整子任务与汇总。
- 当前 EventSource 由具体页面按需连接。如果用户尚未进入相关页面，
  Store 无法持续接收并记录爬虫运行态。
- Store 保存完整运行对象、子任务、日志和汇总，而这些数据已有明确的
  REST 或页面本地所有者。
- 多个未被前端使用的接口和事件增加了维护成本。

本设计采用“REST 提供静态数据和必要的首次状态基线，EventSource 负责
后续动态状态”的混合方案。任务列表是明确例外：任务运行态和顶部统计从
EventSource 首次快照开始即完全由实时通道提供。

## 目标

- 登录期间只维护一个应用级 EventSource 连接，在任意页面都能更新爬虫
  运行态 Store。
- 任务列表只调用任务列表接口；接口只返回卡片和分页需要的静态数据。
- 任务列表顶部统计、任务运行状态、最近运行 ID 和最近运行时间来自
  EventSource，并保存在 Zustand Store。
- 运行记录列表通过一个接口取得静态行、分页总数和首次状态基线；后续状态
  只由 EventSource 更新 Store。
- 运行详情的子任务列表通过接口取得列表与首次状态基线；后续状态由
  EventSource 更新页面本地数据，不保存到全局 Store。
- 保留“接口加载历史日志，EventSource 追加新日志”的模式。
- 精简响应字段、操作接口响应、实时事件载荷以及 Store 数据结构。
- 删除确认无前端消费者的接口、前端类型和实时事件。

## 非目标

- 不改变爬虫调度、抓取、重试和持久化行为。
- 不改变存储任务、影片列表和仪表盘的业务行为。
- 不把运行态持久化到 `localStorage` 或其他浏览器持久层。
- 不引入 WebSocket、事件回放服务或新的独立消息系统。
- 不为子任务建立独立的全量 SSE 快照通道。
- 不进行与本次数据边界无关的通用重构。

## 设计决策

### 1. 应用级实时连接

EventSource 生命周期从页面移到登录后的应用外壳：

1. `AppLayout` 挂载时建立唯一连接。
2. 页面切换、keep-alive 激活和停用不创建或关闭连接。
3. 所有事件先经过统一事件归约器，再通知页面级订阅者。
4. 退出登录或应用外壳卸载时关闭连接并重置爬虫运行态 Store。

这保证用户停留在仪表盘、影片或存储页面时，爬虫任务和运行记录的状态变化
仍会进入 Store。再次进入爬虫页面时，不需要等待新的状态事件才能看到本次
登录会话内的最新状态。

页面级实时 Hook 只处理页面特有的本地数据或恢复动作，不再负责建立全局
连接，也不再复制全局 Store 的更新逻辑。存储任务和影片页面仍可保留自己的
事件订阅行为，但共享同一个应用级连接。

### 2. Store 职责

爬虫运行态 Store 仅保存：

- EventSource 连接状态、最近连接时间和最近一次重同步原因。
- `taskRuntimeById`：任务运行状态、最近运行 ID 和最近运行时间。
- 任务运行态顶部统计，以及任务快照是否准备完成。
- `runRuntimeById`：运行记录的状态、错误、开始时间、完成时间和更新时间等
  会动态变化的字段。

从 Store 移除：

- 完整运行对象。
- 运行详情子任务。
- 运行日志。
- 运行详情汇总。

这些被移除的数据分别由 TanStack Query 或运行详情页面本地状态管理。
Store 仅存在于当前浏览器会话内存中；刷新页面后重新通过 REST 基线和
EventSource 快照初始化，避免恢复陈旧运行态。

Store 更新动作必须区分“替换快照”和“合并增量”：

- 首次任务快照原子替换 `taskRuntimeById` 和顶部统计。
- 单任务事件只更新一个任务，并同步调整或重新计算统计。
- 运行列表或运行详情的 REST 结果可写入对应运行的首次状态基线。
- 运行状态事件只覆盖载荷中的动态字段。
- 运行删除后移除对应运行态。
- 每个实体记录专用的 `state_updated_at`。该值取产生状态变化的运行记录
  `updated_at`；没有数据库更新时间时使用事件创建时间。旧事件不得覆盖新状态。

### 3. REST 与 EventSource 数据所有权

| 页面 | REST 负责 | EventSource 负责 | 动态状态位置 |
| --- | --- | --- | --- |
| 任务列表 | 静态任务行、分页总数 | 顶部统计、任务状态、最近运行 ID/时间 | Zustand Store |
| 运行记录 | 静态运行行、分页总数、首次状态基线 | 后续运行状态、错误、起止时间 | Zustand Store |
| 运行详情 | 运行基础信息、历史日志、子任务分页、首次子任务状态和汇总 | 运行状态、子任务状态、汇总、追加日志 | 运行状态进 Store；其余为页面本地状态 |

静态数据不得因为普通状态事件而重新请求。只有新增或删除静态行、筛选成员
变化、用户主动操作后的静态数据变化，以及异常恢复才允许刷新对应接口。

## 接口设计

### 任务列表

`GET /api/crawler/tasks` 统一返回：

```json
{
  "rows": [],
  "total": 0,
  "page": 1,
  "size": 20
}
```

任务列表行使用专用精简模型，只包含：

- `id`
- `name`
- `storage_location`
- `is_skip`
- `urls`

列表中的 URL 只保留卡片展示和 URL 爬取弹窗需要的字段：`id`、`position`、
`url`、`url_type`、`has_magnet`、`has_chinese_sub` 和 `url_name`。

任务列表响应不再包含 `runtime`，也不再包含任务运行 `status`、旧 `task_id`、
`error_message`、累计抓取数量、`owner_id`、最后运行状态或最后运行时间。
任务编辑页继续使用任务详情接口及其完整编辑模型。

### 运行记录列表

`GET /api/crawler/runs` 统一返回 `{ rows, total, page, size }`。运行列表行只包含：

- `id`
- `task_name`
- `crawl_mode`
- `created_at`
- 首次状态基线 `status`

如果列表 UI 不展示或操作不需要某字段，列表模型不返回该字段。尤其不再返回
空 `logs`、`result`、`resumed_from` 或完整详情时间字段。首次状态写入
`runRuntimeById`，页面渲染时以 Store 中较新的动态状态覆盖接口基线。

### 运行详情

`GET /api/crawler/runs/{run_id}` 返回详情头部需要的基础信息和首次运行状态
基线，不返回空日志数组。

`GET /api/crawler/runs/{run_id}/logs` 保留，用于读取完整历史日志。

`GET /api/crawler/runs/{run_id}/tasks` 返回：

```json
{
  "rows": [],
  "total": 0,
  "summary": {
    "total": 0,
    "completed": 0,
    "waiting": 0,
    "skipped": 0,
    "failed": 0
  }
}
```

实际 `summary` 继续保留页面当前展示和筛选所需的细分状态计数。它与分页行在
同一次请求中取得，删除独立汇总请求。子任务列表行使用专用模型，只保留
表格展示、状态筛选和失败重试需要的字段：实体 ID、展示番号、展示来源、
URL 来源标签、首次状态基线和错误信息。可在抓取过程中发生变化的展示字段
由后续实时补丁更新。

### 操作接口

启动、停止、重启和重试接口只返回操作已受理所需的最小结果，例如运行 ID
和 `accepted`。前端不以操作响应直接修改运行状态，状态变化统一等待
EventSource。

任务删除接口继续返回已删除影片、磁链和云端目录等统计，因为现有成功提示
使用这些数据。创建和编辑任务接口继续返回其调用者实际需要的数据，不在
本次设计中强行改变无关消费者。

## EventSource 事件设计

### `crawler.task.runtime.snapshot`

在以下时机发送当前用户的完整任务运行态：

- 每次 EventSource 连接成功。
- 任务创建后。
- 任务删除后。

载荷包含任务运行态数组、顶部统计、快照生成时间和明确的快照原因
（`connected`、`task_created` 或 `task_deleted`）。任务运行态只包含
`task_id`、`runtime_status`、`latest_run_id`、`last_run_at` 和
`state_updated_at`。
`latest_run_status` 与 `runtime_status` 重复，不再发送。

服务端必须先订阅用户事件队列，再计算并发送快照。快照计算期间产生的增量
事件留在队列中，并在快照之后发送，从而避免快照与订阅之间的事件丢失。

### `crawler.task.status.updated`

单个任务运行态变化事件，字段与快照中的单项一致。全局事件归约器更新
Store，并同步维护顶部统计。

### `crawler.run.status.updated`

替代当前语义过宽的 `crawler.run.updated`。只发送运行 ID 及真正动态的字段：
状态、错误、开始时间、完成时间和更新时间。它不再伪装成缺少多个字段的
完整 `CrawlRun`。

所有页面收到此事件时都会更新 `runRuntimeById`。运行列表当前页存在该 ID
时只重渲染，不请求接口；事件对应未知的新运行 ID 且运行列表当前可见时，
只触发一次列表刷新以取得新的静态行。

### `crawler.run.detail.updated`

继续按运行 ID 发送子任务增量，但每个子任务只发送可变化且页面需要的字段，
包括子任务 ID、状态、错误及可能在抓取后确定的展示字段。事件同时携带该运行
的最新完整汇总。

当更新会影响服务端分页或筛选成员关系、且前端无法仅靠当前页补丁确定新行
位置时，事件设置结构刷新标记。普通已知行状态变化只合并本地数据，不请求
接口。

### `crawler.run.log.appended`

保留现有语义。只有当前打开对应运行详情的页面订阅者追加日志；其他页面不把
日志写入 Store。之后进入详情时，日志接口提供完整历史记录。

## 页面数据流

### 应用启动和重连

1. 用户登录并进入 `AppLayout`。
2. 全局 EventSource 建立连接，Store 标记为连接中。
3. 服务端发送 `system.connected` 和任务运行态快照。
4. Store 原子写入任务运行态、统计，并将 `snapshotReady` 置为 `true`。
5. 后续所有爬虫事件在页面订阅者之前先进入全局归约器。

EventSource 断线时保留最后状态，但标记连接异常。在恢复成功前，依赖精确
运行态的启动、编辑、删除等操作禁用，避免把未知或陈旧状态当作 `idle`。
后端仍保留最终状态校验，防止绕过前端限制。

自动重连后，服务端重新发送完整任务快照。`system.resync_required` 触发受控
重连；当前打开的运行详情额外重新请求基础信息、子任务和日志。异常恢复可以
产生额外请求，正常增量事件不得触发全量刷新。

### 任务列表

1. 页面请求一次任务列表接口。
2. 卡片静态字段来自 Query，运行状态和顶部统计来自 Store。
3. 快照到达前显示“同步中”，且不默认显示空闲状态。
4. 启动、停止或重启成功后只显示“已受理”，等待实时状态事件。
5. 创建、编辑或删除等静态变化成功后刷新任务列表一次。
6. 创建或删除任务时由后端重新推送任务快照，更新顶部总数和各状态数量。
7. 当前可见页面收到 `task_created` 或 `task_deleted` 原因的远端快照时，将同一
   时间窗口内的通知合并后刷新静态任务列表一次；`connected` 快照不额外刷新
   已经执行中的首次列表请求。

### 运行记录

1. 页面请求一次运行列表接口。
2. 接口状态基线写入 Store，静态行与动态状态在渲染层合并。
3. 已知运行的状态事件只修改 Store。
4. 新运行事件若对应当前列表未知 ID，合并同一时间窗口内的重复通知后刷新
   列表一次。
5. 删除运行后从 Query 静态行和 Store 运行态中同时移除该 ID。

### 运行详情

1. 分别读取运行基础信息、历史日志和子任务分页。
2. 子任务响应同时初始化本地列表、总数和汇总。
3. 运行状态通过 Store 覆盖详情接口基线。
4. 子任务事件更新本地列表和汇总，不进入 Store。
5. 行因状态变化不再匹配当前筛选条件时从本地列表移除；可能有新行进入当前
   页但无法确定位置时刷新子任务接口。
6. 日志事件只追加到当前详情，并按时间戳、组件、事件名和消息组成的复合键
   去重。

## 删除项

直接删除以下 HTTP 路由，不保留兼容期：

- `/api/crawler/tasks/count`
- `/api/crawler/tasks/stats`
- `/api/crawler/tasks/statuses`
- `/api/crawler/runs/count`
- `/api/crawler/runs/queue-status`
- `/api/crawler/runs/{run_id}/tasks/summary`

删除以下无消费者的实时契约：

- `crawler.queue.updated`
- 对应前端事件名、类型和未使用发布函数

运行时内部 `queue_status()` 保留，因为仪表盘仍使用它。同步删除前端不再使用
的 API 方法、查询键、响应类型和 Store 动作。共享 `CountResponse` 若仍被存储
模块使用，应移动到合适的共享 API 类型位置，而不是随爬虫计数接口一并误删。

## 错误处理与一致性

- 任务快照未准备完成时，不把缺失状态解释为 `idle`。
- Store 按实体更新时间或事件时间拒绝旧事件覆盖新值。
- 事件解析失败、队列溢出或 Redis 监听异常通过 `system.resync_required` 进入
  统一恢复流程。
- 操作接口成功只代表受理成功；EventSource 是动态状态变化的唯一后续来源。
- 操作失败保留现有错误提示，不修改 Store。
- 页面本地增量无法维持分页或筛选正确性时允许执行一次窄范围刷新。
- 运行详情日志追加需要去重，防止异常重连或恢复刷新产生重复行。
- Store 只在当前登录会话中有效，退出登录必须清空，防止跨用户状态泄漏。

## 测试设计

### 前端

- 验证 `AppLayout` 登录后只建立一个 EventSource，切换页面不会重复连接，
  退出登录会断开并重置 Store。
- 验证爬虫页面未挂载时，任务和运行事件仍会更新 Store。
- 验证首次任务快照原子替换任务运行态和顶部统计。
- 验证旧事件不会覆盖较新状态。
- 验证任务列表只调用 `/tasks`，不再调用 count、stats 或 statuses。
- 验证快照到达前显示同步状态并禁用依赖状态的操作。
- 验证运行列表只调用 `/runs`；已知行状态事件不刷新列表，未知新运行只刷新
  一次。
- 验证运行详情不再请求独立 summary 接口。
- 验证子任务事件只更新当前页面本地列表和汇总，不写入 Store。
- 验证历史日志加载、实时追加和去重。
- 验证断线、自动重连和 `system.resync_required` 恢复路径。
- 更新 `frontend/README.md` 中的全局实时连接、Store 职责和页面数据来源约定。

### 后端

- 验证三个精简列表/详情响应只包含约定字段和分页信息。
- 验证任务运行态快照在连接时发送，并按 owner 隔离。
- 验证先订阅队列再生成快照，快照期间的增量事件不会丢失。
- 验证任务创建和删除后发送新快照。
- 验证运行和子任务事件使用精简载荷并包含必要时间戳。
- 验证被删除路由返回 404。
- 保留并通过爬虫运行时、调度和仪表盘队列状态测试。

### 验证命令

前端运行相关 Vitest、完整 `npm test` 和 `npm run build`。后端运行爬虫 API、
实时事件和运行时相关 Pytest；若这些改动触及共享响应类型，再运行对应存储模块
测试。验证正常状态事件不会额外请求任务或运行列表接口。

## 成功标准

- 进入任务列表时只产生一次任务列表 HTTP 请求，不再请求独立计数、统计或
  状态接口。
- 进入运行记录列表时只产生一次运行列表 HTTP 请求。
- 运行详情不再请求独立子任务汇总接口。
- 用户停留在任意登录后页面时，任务和运行状态事件都能更新 Store。
- 普通状态变化不触发列表接口刷新，页面状态仍能实时更新。
- 子任务状态实时更新但不进入全局 Store。
- 首次加载、断线重连、筛选分页和日志追加仍保持正确。
- 已确认的无用接口、事件、字段、类型和 Store 数据被删除。
